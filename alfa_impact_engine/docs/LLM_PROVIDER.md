# Подключаемый адаптер LLM, v0.3

`app.llm_provider` реализует синхронный HTTP-адаптер протокола chat/completions. По умолчанию он выключен. Импорт модуля, чтение конфигурации и `status()` не делают сетевых запросов. В разработке использованы только `httpx.MockTransport` и синтетические ответы; доступность реального провайдера не проверена.

## Конфигурация

Переменные процесса читаются через `ProviderConfig.from_env()`. Модуль сам не загружает `.env`.

| Переменная | Значение / правило |
|---|---|
| `LLM_ENABLED` | `false` по умолчанию; включение — `true` или `1` |
| `LLM_BASE_URL` | Базовый HTTPS URL с API-префиксом, например `https://provider.example/v1` |
| `LLM_MODEL` | Точное разрешённое имя из ТЗ §1.2; используется существующий allowlist |
| `LLM_API_MODEL` | Явный технический ID модели у провайдера; автоматически не подбирается |
| `LLM_API_KEY` | Ключ для Bearer Authorization; не выводится в статусе, логах или repr конфигурации |
| `LLM_TIMEOUT_SECONDS` | По умолчанию 20, диапазон 1–60 секунд |
| `LLM_MAX_OUTPUT_TOKENS` | По умолчанию 1500, диапазон 128–4000 |
| `LLM_MAX_CALLS_PER_DAY` | По умолчанию 50, диапазон 1–1000 |
| `LLM_INPUT_RUB_PER_1M` | Необязательная неотрицательная цена миллиона входных токенов |
| `LLM_OUTPUT_RUB_PER_1M` | Необязательная неотрицательная цена миллиона выходных токенов |
| `LLM_DAILY_BUDGET_RUB` | По умолчанию 500; положительное число |

API-префикс сохраняется, затем добавляется `/chat/completions`. HTTPS обязателен, кроме явно заданного loopback HTTP: `localhost`, `127.0.0.1`, `[::1]` и других loopback IP. URL с логином, паролем, query, fragment, пробельными и управляющими символами отклоняется. Proxy-переменные среды не используются, редиректы не выполняются, автоматических повторов нет.

Имя из allowlist и технический ID — отдельные поля. Адаптер проверяет разрешённое проектом имя, но не может доказать, что провайдер действительно обслуживает этим техническим ID нужную модель. Это проверяется перед включением. Без любого обязательного поля `configured=false`, а попытка вызова возвращает `NOT_CONFIGURED`.

## Python API

```python
from app.llm_provider import LLMProvider, ProviderConfig, ProviderUnavailable

config = ProviderConfig.from_env()
provider = LLMProvider(config)
status = provider.status()  # Только конфигурация; connection_verified всегда False.

# Только в явно выбранном режиме LLM и после настройки доступа:
# result = provider.extract(messages, schema)
# result.content — строка с JSON-объектом;
# result.metadata — безопасные ID запроса, модель, usage, время, оценка стоимости.
```

`extract(messages, schema)` отправляет только роли `system/user/assistant` с текстовым `content`, нормализованную схему в `response_format.type=json_schema`, `strict=true` и лимит `max_tokens`. Публичная `strict_json_schema(schema)` создаёт копию схемы, удаляет `default`, рекурсивно включает все объявленные свойства объектов в `required` и устанавливает `additionalProperties=false`. Nullable-поля сохраняют `anyOf` с `null`, но должны явно присутствовать в ответе; поля-массивы без значений передаются как `[]`. `$defs` и `$ref` сохраняются. Исходная Pydantic-схема не меняется. Эту же функцию можно использовать при вставке схемы в промпт. Свободные словари при таком закрытии объектов не поддерживаются; контракт извлечения задаёт конечный набор полей.

Провайдер должен поддерживать этот формат и используемые ключевые слова JSON Schema; преобразование схемы не подтверждает совместимость конкретного endpoint. Смена на свободный текст или иной формат при ошибке не выполняется. Совокупный сериализованный запрос ограничен 128 000 байтами.

Ответ ограничен 1 000 000 байтами; сжатые ответы отклоняются, клиент запрашивает `Accept-Encoding: identity`. Разрешена одна завершённая choice с `finish_reason=stop` и непустым строковым `message.content`, содержащим JSON-объект. Отклоняются оборванные ответы, refusals, content filter, неизвестная структура, дубли ключей и JSON `NaN/Infinity`. Семантику и предметную JSON Schema проверяет следующий слой приложения: адаптер не заменяет extraction/output validator.

HTTPX применяет заданный таймаут к сетевым фазам соединения, чтения, записи и ожидания пула. Дополнительно адаптер проверяет общее прошедшее время после получения заголовков, каждого блока тела, завершения тела и перед успешным результатом. Это предотвращает принятие запоздавшего ответа, включая пустое тело. Синхронная реализация не прерывает заблокированную фазу ровно по общей wall-clock границе: фактическое время возврата ошибки может превысить настройку до завершения текущей фазы или её таймаута. Поэтому настройку нельзя описывать как гарантированную общую длительность HTTP-запроса.

`ProviderConfigurationError` содержит безопасные `code=INVALID_CONFIGURATION` и `field_name`. `ProviderUnavailable.code` сообщает `DISABLED`, `NOT_CONFIGURED`, `INVALID_REQUEST`, `REQUEST_TOO_LARGE`, `HTTP_ERROR`, `TIMEOUT`, `NETWORK_ERROR`, `INVALID_RESPONSE`, `RESPONSE_TOO_LARGE`, `TRUNCATED`, `REFUSED`, `DAILY_LIMIT` или `BUDGET_EXCEEDED`. Тела ошибок провайдера, URL, ключи и тексты промптов не попадают в исключения и собственные логи адаптера. При глобальном DEBUG/INFO-логировании HTTP-клиента отдельно проверьте настройки инфраструктурных журналов.

Метаданные содержат nullable `prompt_tokens`, `completion_tokens`, `estimated_cost_rub`. Отсутствие usage означает неизвестные значения, а не ноль. Успешный HTTP-ответ не подтверждает достоверность новости или вывода. `status()` сообщает только `enabled/configured`, имя модели, протокол и режим учёта; он не выполняет health probe и не объявляет подключение проверенным.

## Пределы бюджета

Все экземпляры адаптера по умолчанию используют один блокируемый ledger процесса. До отправки резервируется одна попытка; по UTC-дате действует `LLM_MAX_CALLS_PER_DAY`. Ошибочные запросы также расходуют попытку. Параллельные потоки не могут одновременно пройти лимит сверх заданного числа.

При наличии обеих цен режим — `ESTIMATED_PROCESS_LOCAL`: до отправки резервируется оценка по байтам запроса с запасом на оформление и максимальному выходу. Если оценка превышает оставшийся денежный предел, запрос не отправляется. При корректном usage резерв заменяется оценкой по сообщённым токенам. При ошибке или неизвестном usage денежный резерв сохраняется.

Если хотя бы одна цена неизвестна, режим — `MONEY_UNKNOWN`: денежный лимит не контролируется; остаются лимит вызовов, максимальный выход и таймаут. Нельзя описывать этот режим как соблюдение общего бюджета ключа 500 ₽/сутки.

Даже при известных ценах это оценочный ограничитель одного процесса: он не учитывает другие процессы, воркеры, перезапуски и пользователей того же ключа. Особенности биллинга, скрытые токены и фактические тарифы провайдера могут отличаться; финансовая гарантия не предоставляется. Для общей квоты потребуются persistent/shared ledger и сверка с провайдером. Запрос, начавшийся до полуночи UTC, учитывается на дате начала.

## Проверка без внешнего доступа

`LLMProvider(config, transport=httpx.MockTransport(handler), ledger=UsageLedger())` позволяет тестировать транспорт и отдельную квоту. Тесты проверяют выключенный режим, allowlist, явный API model ID, конфигурацию URL, безопасные ошибки, HTTP/timeout/refusal/truncation, размер ответа, лимиты и блокировку параллельных резервов. Реальные ключи и провайдер для этого не нужны.

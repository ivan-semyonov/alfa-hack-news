**Версия:** 1.0.0 · **Дата фиксации:** 21 октября 2026 года · **Статус:** согласованный проектный baseline для начала разработки; реализация по этапам.  
**Проект:** «Альфа‑Будущее», трек «Новостная аналитика для принятия бизнес‑решений».  
**Источник обязательных требований:** файл организаторов «Альфа Хак_Новостная аналитика.pdf», 19 страниц. Ссылки `[Кейс, с. N]` означают номера страниц из документа.

## 0. Паспорт проекта и решение о границах

### 0.1. Проблема и ценностное предложение

Руководителю крупной компании недостаточно агрегированной ленты новостей: он хочет понять, **каким образом конкретное внешнее событие может затронуть его бизнес**, насколько обоснован вывод, какие есть риски и возможности, что думают аналитики Альфа‑Банка, и какой вопрос или действие целесообразно рассмотреть [Кейс, с. 2, 4, 14].

**Наш продукт (DES):** `Agentic Business Impact Engine` — сервис, который соединяет новости и аналитику банка с проверяемой моделью зависимостей компании; агент формирует гипотезы воздействия, исследует источники, находит объяснимые `Impact Path`, оценивает доказательность, формирует персональные инсайты и позволяет задать уточняющий вопрос.

**Главный объект результата:** `ImpactPath`, а не LLM-резюме. Пример: `ограничение экспорта → ресурс → возможный поставщик → закупки → производство → KPI`. Путь **потенциальный** до подтверждения каждого звена.

**Обещание продукта:** «Объяснить возможный канал воздействия и основания для дальнейшего решения». **Не обещаем:** достоверно предсказывать прибыль; восстановить всю внутреннюю ERP, поставщиков и технологические процессы по обезличенному ОКВЭД; предсказывать «чёрных лебедей»; автоматически принимать управленческие решения.

### 0.2. Фиксированная граница MVP

**Включено в MVP:** выбор компании; импорт/чтение предоставленных признаков; приём и парсинг новости; нормализованное событие; первичная персонализация; 2–3 типовых отраслевых шаблона; многоуровневый граф (`FACT / INFERENCE / HYPOTHESIS / TEMPLATE`); обнаружение допустимых путей воздействия; Alfa RAG с источниками; один самостоятельно реализованный агент с инструментами и self-check; ранжирование новостей; полный веб-сценарий с объяснением и диалогом; evaluation и Docker.

**Не включено в обязательный MVP:** полноценный digital twin; эконометрический расчёт «−17% выручки» без исходных коэффициентов; все ОКВЭД России; автоматический анализ поставщиков второго/третьего уровня без доказательств; сложная многоагентная система; GNN/Neo4j; собственные поисковые и embedding-модели без проверки правил; продакшен-интеграция с реальным интернет-банком.

**Планируемое развитие:** сценарии, fragility/redundancy, cross-impact, weak signals, расширенная роль CFO/CEO, подтверждение контекста пользователем.

### 0.3. Нерешённые внешние вопросы

1. Формат проверки unseen news: текст, URL, файл, автономный поиск; интернет во время проверки? [ASSUMPTION].
2. Допустимость внешних не-AI API, embedding/reranker моделей и локальных моделей; **до ответа использовать только разрешённые LLM**, а RAG стартует на полнотекстовом поиске.
3. Период/единица `PAY_AMT` и смысл платёжной сети; неизвестно, можно ли считать долю платежей экспозицией.
4. Точная форма рынка/доли рынка для обезличенных компаний: не выдавать долю внутри датасета за долю всего рынка.
5. Нужно проверить фактические имена файлов: в кейсе на с. 16 заголовки «Физические лица» и «Платежи» ссылаются на одинаковый `df_Fid_Uid_link_hack.csv`; это выглядит как опечатка, **не исправляем молча**.
6. Актуальная дата/время конечной сдачи и формат защиты не приведены в 19-страничном ТЗ; не приравнивать дату рекламного объявления/регистрации к дедлайну кода.
7. APQC/SCOR рассматриваются как методологические ориентиры. Не копировать целиком защищённые базы/онтологии; лицензию на машинное использование проверить отдельно.

## 2. Функциональная модель

### 2.1. Пользователи

Целевые роли по кейсу [с. 5]: собственник, CEO, CFO, главбух, казначей, другие ЛПР. Система моделирует `user_role` отдельно от `company_id`. Для MVP основной универсальный профиль `EXECUTIVE`, role selector добавляется простой настройкой; расширенная адаптация ответов CFO/CEO — после стабилизации MVP.

### 2.2. Пользовательские сценарии

- **UC-01:** выбрать юридическое лицо → просмотреть известные признаки (со статусом достоверности).
- **UC-02:** открыть ленту значимых событий; показать причину персональной релевантности.
- **UC-03:** вставить текст/URL новой новости → получить статус выполнения и результат.
- **UC-04:** открыть карточку `Insight` → факт, затронутые процессы, риски, возможности, рекомендации, источник Альфы.
- **UC-05:** нажать «Почему?» → `ImpactPath`, тип каждого ребра и доказательство/неизвестность.
- **UC-06:** задать уточняющий вопрос по сохранённому анализу; агент использует **тот же контекст и те же источники**, а не свободный общий чат.
- **UC-07:** сменить компанию → получить новое ранжирование/слабое либо отсутствующее воздействие.
- **UC-08:** пользователь подтверждает/опровергает предполагаемую связь (в качестве расширения: обязательные история и роль подтверждающего).
- **UC-09:** администратор/тестировщик просматривает шаги агента, затраты, ошибки и источник каждого утверждения без раскрытия скрытого chain-of-thought.

### 2.3. Нефункциональные требования (DES — проектные цели, не критерии PDF)

- Детерминированность структурных вычислений и воспроизводимость на одинаковых фикстурах.
- Не допускать межклиентского доступа через API: все запросы графа/инсайтов ограничены авторизованным `company_id`.
- Отслеживать `source_id`, период данных и версию отраслевого шаблона.
- Время и стоимость каждой стадии логируются; `timeout`, `budget`, `max_steps`, fail-closed для сомнительных источников.
- Недоступность LLM или поиска не должна приводить к выдуманному инсайту: показать явный degraded-state.
- Если значимый канал не установлен, вернуть «Нет подтверждённого маршрута», а не «риска нет».

**Платежи:** `PAYER`, `BENEFICIARY`, `PAY_AMT`, `PAY_CNT`. **Внимание:** PDF использует в заголовке платежей то же имя файла, что и для связей физлиц. Loader проверяет схему по заголовкам CSV, а не гадает по имени.

Правила интерпретации:

- `PAYER → BENEFICIARY` = наблюдаемое агрегированное финансовое взаимодействие, **не доказательство** supplier/customer relationship и не прямое измерение материального потока.
- `FTS_COUNTRY_NAME` = страна в данных ФТС, **не доказательство** закупки конкретного материала.
- `CL_PRODUCT_LOA_MARK` = наличие кредитного продукта, **не сведения** о текущем долге, ставке и CAPEX.
- `GROUP_ID` = связь группы внутри данных; перенос выводов на каждое юрлицо требует конкретного маршрута.
- Обезличенные ID нельзя деанонимизировать через интернет и нельзя связывать с реальными юридическими лицами [с. 16].

### 3.2. Внешние новости

`NewsDocument`: текст, автор/издатель, дата/время публикации, время загрузки, URL, язык, content hash, разрешение на обработку, оригинальные утверждения. `Event` отделён от документов: много статей могут описывать одно событие; статья может включать несколько событий. Ингестор должен поддерживать входной текст, а URL — отдельным адаптером по правилам источника. RSS/news API при доступности; бесплатный demo fixture как fallback.

### 3.3. Альфа-аналитика [с. 17]

Предоставлены темы: недельная инфляция, облигации, золото, тактический взгляд, commodities, ключевая ставка, рынок труда, потребление, ВВП. Индексировать файл → page/chunk → поисковая запись; хранить автора и дату документа; цитата должна ссылаться на файл, страницу и фрагмент. Отсутствие релевантной аналитики явно обозначается `NOT_FOUND`.

### 3.4. Отраслевые шаблоны (DES)

`IndustryKnowledgeBase`: авторская компактная онтология типовых процессов. Методологические ориентиры: APQC Process Classification Framework и ASCM SCOR Digital Standard, а не буквальное копирование документации. Приоритетные классы для пилота **выбрать после анализа распределения ОКВЭД**: кандидатные шаблоны manufacturing, trading, services/IT. Каждый шаблон содержит: `template_id`, `industry_codes`, `version`, `processes`, `dependencies`, `scope`, `source_refs`, `limitations` и `status=TEMPLATE`, пока не подтверждена применимость к клиенту.

Официальные справочные материалы (проверены 21.10.2026):
- APQC: https://www.apqc.org/resource-library/resource-collection/apqcs-process-classification-framework-pcf-cross-industry-and
- APQC: https://www.apqc.org/resource-library/resource-listing/apqc-process-classification-framework-pcf-cross-industry-excel-12
- ASCM SCOR: https://www.ascm.org/corporate-solutions/standards-tools/scor-ds/
- SCOR processes: https://scor.ascm.org/

**Никогда не превращать отраслевой template в `FACT` простой генерацией LLM.**

### 3.5. Реестр происхождения (`EvidenceStore`)

Источники `BANK_FIELD`, `BANK_PAYMENT`, `BANK_RELATION`, `NEWS`, `ALFA_REPORT`, `INDUSTRY_TEMPLATE`, `PUBLIC_SOURCE`, `USER_CONFIRMATION`; evidence хранит source, source span, version, as_of, права использования и payload hash. `USER_CONFIRMATION` — отдельный источник, не автоматически объективная истина.

## 4. Модель знаний и граф

### 4.1. Разграничение статусов

- `FACT`: прямо зафиксированное свойство/отношение в конкретном источнике (не значит, что источник безошибочен).
- `TEMPLATE`: типовой отраслевой процесс/отношение, применимость к компании не подтверждена.
- `INFERENCE`: результат алгоритмического вывода, обязательно указать основание и правило.
- `HYPOTHESIS`: предполагаемое отношение/канал, требующее проверки.
- `REJECTED`: проверенный отрицательный результат или опровергнутая гипотеза, с источником опровержения.

**Разделять:** 1) уверенность в наличии связи; 2) значимость воздействия при наличии связи; 3) неопределённость сценария. Никогда не сводить в одно число `87% вероятность проблемы`, если нет калиброванной статистики.

### 4.2. Типы узлов (начальный allowlist)

`COMPANY`, `INDUSTRY`, `PROCESS`, `PRODUCT`, `RESOURCE`, `COMMODITY`, `TECHNOLOGY`, `LOCATION`, `FINANCIAL_INSTRUMENT`, `KPI`, `EVENT`.

### 4.3. Типы рёбер (начальный allowlist)

`OPERATES_IN`, `OWNS_PROCESS`, `PRODUCES`, `REQUIRES`, `DEPENDS_ON`, `USES`, `HAS_PAYMENT_TO`, `LOCATED_IN`, `HAS_FINANCIAL_PRODUCT`, `PART_OF_GROUP`, `CONTRIBUTES_TO`, `AFFECTS`, `RELATED_TO`.

**Договорённость направления:** `PROCESS --REQUIRES--> RESOURCE`, `PRODUCT --DEPENDS_ON--> PROCESS`, `KPI --DEPENDS_ON--> PRODUCT`. Impact распространяется от ресурса к потребителю **по обратному направлению зависимостей**; traversals уважают тип ребра. Платёжные и групповые связи сами по себе не участвуют в propagation до установления функциональной семантики.

### 4.4. Структурные объекты

`GraphNode`: `id, type, label, company_scope?, attributes, knowledge_status, evidence_ids, valid_from?, valid_to?`.

`GraphEdge`: `id, source_id, target_id, relation, knowledge_status, evidence_ids, valid_from?, valid_to?, dependency_strength?, criticality?, substitutability?, inference_rule_id?`.

`ImpactPath`: `id, event_id, company_id, node_ids[], edge_ids[], channel, evidence_ids[], path_status, impact_level, confidence_band, assumptions[], affected_kpis[]`.

### 4.5. Вычислительная роль графа

Граф нужен для: поиска multi-hop путей воздействия; объяснимости; выявления общих точек отказа; дедупликации контекста и хранения результативных исследований. **Не нужен** просто для RSS, RAG или суммаризации. Предусмотрен baseline без графа для доказательства added value.

**MVP propagation:** вручную проверенный список допустимых связей; reverse dependency traversal с ограничением глубины/ветвления; никакой транзитивности по произвольному `RELATED_TO`. Алгоритм возвращает **кандидатов воздействия**, а не гарантированные причинно-следственные эффекты.

### 4.6. Скоринг

Не вводить псевдоточность. Сначала оценивать независимо:

1. `relevance`: связь темы/объекта события с компанией, подтверждённые и шаблонные признаки;
2. `impact_severity`: LOW/MEDIUM/HIGH/UNKNOWN при условии маршрута, основание явно показывается;
3. `evidence_grade`: VERIFIED/MIXED/HYPOTHETICAL/INSUFFICIENT;
4. `urgency`: NOW/SOON/MONITOR/UNKNOWN;
5. `coverage`: сколько значимых звеньев отсутствует.

Впоследствии возможны калиброванные численные модели на размеченных парах «компания—событие». Без gold labels не делать probability 0.81.

## 5. Процессы Event / Agent / Impact

### 5.1. Event intelligence

`ingest → normalize(text/metadata) → extract structured facts → deduplicate → classify channels → store event`. Предусмотреть сопоставление времени факта со временем публикации; повторные новости об одном событии объединяются с сохранением множественных источников, не стирая противоречия.

Типы impact channels: `SUPPLY`, `DEMAND`, `FINANCE`, `REGULATION`, `TECHNOLOGY`, `LABOR`, `INFRASTRUCTURE`, `COMPETITION`, `GEOGRAPHY`, `MACRO`. Несколько каналов разрешены. Неизвестный тип → `OTHER` + исследование, а не отказ.

### 5.2. Agent planner и состояние

`AgentRun`: run_id, company_id, event_id, role, tool_budget, token_budget, state_version, hypotheses, observations, visited_actions, evidence_ids, paths, pending_questions, errors, status, started_at, finished_at. Конкретные лимиты (`MAX_STEPS=8`, `MAX_EXPANSIONS=4`, `MAX_SEARCHES=3`) — **стартовые технические значения**, требуют тестирования.

Tool registry (read-only): `get_company_profile`, `get_company_network`, `get_business_subgraph`, `retrieve_alfa_analytics`, `search_news`, `search_public_sources`, `expand_graph`, `find_impact_paths`, `evaluate_impact`, `verify_claims`.

Поток: 

1. составить несколько альтернативных гипотез;
2. определить доказательства для каждой;
3. выбрать инструмент с наибольшей полезностью по бюджету;
4. получить и записать проверяемый `Observation`;
5. обновить граф: FACT отдельно от INFERENCE/TEMPLATE;
6. построить пути, проверить семантику и источники;
7. обратиться к Альфа RAG, скорректировать версии;
8. провести `self_check` и записать `AgentStep`;
9. опубликовать инсайт или abstain/needs_more_data.

Запрещается выставлять пользователю приватные рассуждения LLM. Трасса — **структурированный журнал наблюдаемых действий**, вызовов, результатов и источников [Кейс, с. 10].

### 5.3. Alfa RAG

Порядок: upload/index → page extraction → chunks с file/page/time → lexical search (MVP) → re-rank по приоритету темы/даты → цитирование → `alfa_review` (`SUPPORTS`, `REFINES`, `CONTRADICTS`, `NOT_FOUND`). Семантический поиск — после разрешения embedding-модели. Материал может уточнять макросценарий, но не доказывает свойства конкретной компании, которых в нём нет.

### 5.4. Insight

Обязательные поля: `what_happened`, `why_for_company`, `risk_items[]`, `opportunity_items[]`, `impact_paths[]`, `alfa_view{status,quote_ref,statement}`, `actions[]` (каждая связана с path_id или явным data-gap), `knowledge_gaps[]`, `sources[]`, `agent_run_id`. Output schema запрещает нецитируемые количественные утверждения.

### 5.5. Уточняющий диалог

Вопрос пользователя прикреплён к `insight_id` и `company_id`. Retrieval выполняется в разрешённых источниках с ограничением компании. Ответ должен ссылаться на сохранённый контекст, явно отличать новые факты от повторно использованных и не осуществлять финансовые операции.

## 8. Контроль качества и безопасность

### 8.1. Минимальный golden set

Команда вручную составляет не менее **24 комбинаций событие×компания** (целевая рабочая цифра, не задана кейсом): не менее шести impact channels, положительные/отрицательные пары, слабые косвенные связи, заведомо нерелевантные новости, противоречия, отсутствующие поставщики, дубликаты и новый тип события. `evaluation/golden_cases.json` фиксирует ожидаемые `impact_channel`, `relevance`, `path_exists`, допустимые статусы доказательств, запрещённые утверждения.

### 8.2. Метрики

- `event_extraction_structural_validity`: % валидных JSON и полнота fact fields;
- `news_precision@k`, `news_recall@k`: только при ручной разметке релевантности;
- `path_validity_rate`: доля найденных путей без запрещённых типов рёбер;
- `unsupported_claim_rate`: экспертная выборочная проверка;
- `citation_coverage`: % существенных claims с проверяемой source span;
- `abstention_quality`: корректные отказы при отсутствии данных;
- `agent_completion_rate`, `tool_error_rate`, latency, token spend;
- `user_feedback`, relevance drift по отраслям;
- `graph_ablation_delta`: качество с графом против одинакового LLM baseline.

### 8.3. Безопасность

- Внешний текст/новости/материалы RAG считаются **недоверенным контентом**, а не системными инструкциями (защита от prompt injection).
- Агенту доступны только allowlisted read-only tools; никаких денежных операций, записи пользователю в банк, отправки данных наружу без разрешений.
- Синтетические IDs компании; секреты только в `.env`, `.env` исключается из Git. Логи должны редактировать PII/платёжные детали.
- Поиск с tenant isolation, rate limiting, защита от SSRF через URL ingestor, лимиты размера контента, MIME whitelist, timeouts.
- Логи агентских шагов содержат параметры инструмента без секретов, outcome, evidence IDs, duration и стоимость; не раскрывают скрытые reasoning-трассы модели.
- Различать даты: документ аналитиков может быть историческим, даже если текущий день позднее.

### 8.4. Тесты, которые должны блокировать сдачу

1. Из платежей без иных сведений **не появляется** отношение `SUPPLIES`.
2. Отраслевой шаблон **не превращается** в подтверждённый факт компании.
3. Новость без маршрута не возвращает `HIGH IMPACT`.
4. Условная цепочка явно помечена как условная.
5. Новость не может переопределить инструкции агента через prompt injection.
6. Уточняющий запрос не может получить данные другой компании.
7. Alfa RAG без релевантного материала возвращает `NOT_FOUND`, а не случайную цитату.
8. На новой новости одинаковый парсер выдаёт структурно валидный результат.
9. У каждого существенного утверждения есть источник или флаг `UNVERIFIED`.
10. Docker clean install поднимается, OpenAPI доступна.

| Владелец | Зона | Проверяемый результат |

### 10.1. Граф зависимостей работ

`Schemas+Fixtures → API/DB → Event+Alfa RAG → Baseline → Graph+Templates → ImpactPaths → Agent → UI+QA → Release`. Процессный граф проектируется после анализа реальных ОКВЭД, но **первый графовый unit test** делается сразу на синтетике, чтобы заранее проверить фундаментальную архитектуру.

### 10.2. Первая инженерная итерация, старт прямо сейчас

**Задача DEV-000:** создать этот документ, репозиторий и список открытых вопросов. **DEV-001:** Pydantic-схемы Company/Event/Node/Edge/ImpactPath; строгий allowlist. **DEV-002:** синтетические две компании, одна с зависимостью от ресурса X, другая без. **DEV-003:** простой NetworkX path finder, только допустимые отношения, никаких платежей как поставки. **DEV-004:** FastAPI `/api/analyze` для **структурированного Event** и Swagger. **DEV-005:** unit tests на положительный, отрицательный и неподтверждённый случаи. **DEV-006:** Docker Compose и README. **DEV-007 (следующий после проверок):** actual CSV importer + реальный Company Service.

**Первая демонстрация работоспособности:** отправить одну и ту же синтетическую новость двум компаниям; у первой обнаружить помеченный гипотетический путь, у второй не найти доказательного пути. Ни одно численное значение не выдавать как реальную вероятность. Сервис пока не использует внешнюю LLM — это честный foundation этап.

## 11. Контроль изменений концепции

Любое расширение требует короткого `Decision Record`: почему, какую метрику улучшает, сложность, как откатить. Замена PostgreSQL на graph DB допустима только при подтверждённом масштабе. Использование complex scenario agent допустимо только после успешного unseen-news теста M2. Инвестиция в «уникальность» без измеримого преимущества перед baseline запрещена; защиту строить вокруг качества анализа.

## 13. Крупные риски, план реагирования

| Риск | Вероятный ущерб | Ограничитель / fallback |
|---|---|---|
| Недостаточно сведений для детализации процессов | Выдуманный digital twin | `TEMPLATE` и explicit missing data; stop expansion |
| Платёж = поставка | Ложный причинный путь | Платёж не участвует в propagation без подтверждённой роли |
| Graph explosion | Долгий анализ и ошибка | Ограничения depth/branch, hypothesis first |
| Graph path ≠ causal effect | Ложная точность KPI | Только exposure/scenario; не денежный прогноз без входных данных |
| Агент бесконтрольно цикличен | Стоимость/latency | steps, retries, visited actions, tool budgets |
| Prompt injection в новостях | Утечка/обход правил | Read-only tools, context isolation, untrusted content treatment |
| Аналитика Альфы декоративна | Потеря существенного критерия | Review stage, `NOT_FOUND`, test change-of-conclusion |
| Нет работы на unseen news | Провал критерия №5 | Held-out tests + OTHER channel fallback |
| UI опережает API | Нет живого прототипа | Swagger + фиксированные контракты + ранняя интеграция |
| Не успевают трое | Полурабочая система | M0 → M1 → M2, жёсткий scope, M3 optional |
